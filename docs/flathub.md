# Publishing on Flathub

Status (2026-09-28): not submitted. The license metadata is fixed (MIT everywhere, matching
`LICENSE`); what stands between us and a submission is below, with the decisions that are
Corey's.

## What Flathub requires

From <https://docs.flathub.org/docs/for-app-authors/requirements>:

- **Built from source.** "All source available submissions must be built entirely from source
  code", the app and every dependency in the manifest.
- **No network while building.** Every source is listed in the manifest (URL + checksum) and
  fetched before the build.
- **A redistributable license, correct in the MetaInfo.** Done: `MIT`.
- Downloading code at runtime is not addressed in the requirements, but reviewers look at it.

## Where we are

`flatpak/com.corpetty.mnemosyne.yml` repackages our release `.deb`: the Tauri binary is not built
from source, so it cannot be submitted as it is. It is fine for our own `.flatpak` download.

On first launch the app runs `uv sync` to install the Python backend into a venv (about 300 MB
for the base install; with an NVIDIA driver, the GPU extra adds torch, WhisperX and NeMo, several
GB). That is code downloaded at runtime.

## What a submission needs

1. **The Tauri app from source.** A manifest that builds `src-tauri` with the Rust SDK extension
   (`org.freedesktop.Sdk.Extension.rust-stable`) from vendored crates (`cargo-sources.json`
   generated by flatpak-builder-tools' `flatpak-cargo-generator.py` from `Cargo.lock`), and the
   SvelteKit frontend with the Node extension from vendored packages (flatpak-node-generator; pnpm
   support must be checked, or the frontend switched to npm for this build).
2. **The Python backend inside the Flatpak** instead of installed at runtime: Python 3.13 and the
   base dependencies as manifest modules (flatpak-pip-generator from `uv.lock`, exported with
   `uv export`). Some wheels (onnxruntime, tokenizers, sqlcipher3) are binary-only on PyPI; whether
   Flathub accepts those wheels, or they must build from source (onnxruntime from source is a
   very large build), is the main open question to raise with the reviewers.
3. **The GPU extra.** torch with CUDA and NeMo are far too large and binary to build from source.
   Options: keep installing them at runtime only when the user asks for GPU support (an explicit,
   visible opt-in), or offer GPU transcription only in the AppImage/deb/rpm and keep the Flathub
   build CPU-only (Parakeet on ONNX Runtime, which is our default transcriber anyway).
4. **Sandbox permissions to justify** in the submission: `--filesystem=home` (Obsidian vaults
   anywhere), PipeWire and PulseAudio (recording), `--device=all` (GPU), `--share=network` (LLM
   providers), the keyring, notifications and the tray.
5. **CI**: a workflow that regenerates the source lists and builds the Flathub manifest with
   `flatpak-builder --sandbox`, runs `flatpak-builder-lint`, and smoke-tests the result.

## Decisions for Corey

- Is a CPU-only Flathub build (GPU via the other packages, or an explicit in-app opt-in download)
  acceptable?
- Ask the Flathub reviewers first (a Matrix/Discourse question before the PR) whether binary
  PyPI wheels for onnxruntime and friends are acceptable? That answer decides how much work
  item 2 is.
- Submitting opens a public PR on github.com/flathub/flathub under your account: only on your
  go-ahead.
